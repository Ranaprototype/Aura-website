## Proposed architecture — design only

Use one Express modular monolith, existing React SPA and one authoritative PostgreSQL database. Keep a same-origin API, typed request/response contracts and common validation; route handler → identity/authorization → domain service → repository/transaction. Frontend owns interaction and presentation, not permissions, prices, commitments or state transitions. Import other modules through explicit service interfaces, not direct table writes. Do not create empty services, tables or a queue just to represent the roadmap.

| Domain owner | Responsibility and dependency rule |
|---|---|
| Identity and participants | Auth verifies identity; Users owns identities/profiles; Customers, Sellers, Manufacturers own scoped memberships and capabilities. Admin uses the same authorization boundary, never bypasses it. |
| Marketplace | Categories and Products own taxonomy, listings and approved variants; Inventory owns reservations; Cart requests quotes; Orders commits immutable price/currency snapshots with inventory atomically. Shipping owns fulfillment transitions. |
| Payments and refunds | Only a future separately approved hosted provider flow. Server creates checkout from verified order; authenticated, signature-verified and idempotent provider events drive settlement. Refunds require authorization and an audit trail. Never accept raw card fields. |
| Creation and demand | AI Design and 3D Customization own versioned design assets; Community shares authorized revisions; Product Lab gathers proposals and demand signals, not binding orders. Manufacturing owns verified quotes, thresholds and commitments with human approval. Future automotive customization consumes approved capabilities. |
| Platform operations | Notifications consume committed events; AI Agents call scoped application commands, not the database. Sensitive manufacturing, refund, admin and agent actions require recorded human approval. Audit/Security records sanitized actor, operation, target and outcome. |

Use FK and uniqueness constraints at real boundaries, integer minor units plus currency (or explicit decimal scale), timezone-aware timestamps, and transactions/idempotency keys for stock, orders and commitments. Migrations run with a dedicated migration role; runtime is non-owner with scoped grants, monitoring read-only and admin credentials out of the process. Redis, if later justified, holds only disposable caches/jobs. Store future private assets outside Postgres with access-controlled object references; enforce ownership, type/size limits and short-lived signed URLs. No speculative schema or external provisioning now.

## Phase 0 implementation plan — not authorized by this audit

1. **Contain payment and identity risks first.** Replace card capture, simulated sign-in/payment/order confirmation and misleading CTAs with truthful unavailable states; preserve layouts and non-sensitive design interactions. Propose targeted deletion of `holo-checkout` without reading, logging or copying the value. Coordinate legacy-data handling and incident evidence with owners; code cannot erase other origins/backups. Disable capture/proxy by default. Gate: no sensitive inputs, misleading success or sensitive telemetry on any reachable route, including deep links.
2. **Repair local boot and trust boundaries.** Validate config before clients initialize, split app factory/listener, add relative API proxy, generic typed errors, liveness vs least-privilege readiness, limits, security headers and origin checks. Restrict or remove public diagnostic routes/policies using a reviewed forward migration (never edit applied history). Verify old consumers, permission changes and rollback before applying anywhere. Decide the identity provider/session model in a separate review; meanwhile deny protected actions.
3. **Make checks reproducible.** Pin supported Node and pnpm; triage runtime vs tooling advisories (including impact of overrides and patched Wouter). Upgrade in small tested units. Add CI for frozen install, TS including config, build and advisory policy. Set an explicit test root covering server and client. Use isolated local PostgreSQL fixtures only: migration replay/grants, positive and negative policy checks, safe API status/errors, and serialized state/ownership invariants as implemented. Add browser regressions for navigation, design controls, keyboard/mobile, disabled checkout, sensitive storage absence and false confirmation. No production credentials or real transactions. Gate: executed tests and reviewed exceptions, never an empty green suite.
4. **Document and rehearse operations.** Document module ownership, API/DB contracts, environment matrix (local/test/private staging/production), retention, backup/restore, secrets/rotation, redacted logging/alerts, worker/email requirements and approval/rollback procedures. Keep future integrations off. Obtain separate human approval before any external target verification. No signing off on real auth/commerce before they exist.
5. **Acceptance.** Preserve baseline and UI regression evidence, record commits and PR review, exact test outcomes, dependency disposition and incident ownership. Private staging and target-side evidence remain **PENDING**. No live payments, production or next phase until explicit review.

Compatibility constraints: preserve existing URLs while fixing matcher precedence, do not trust browser carts for price/stock, do not turn demo orders into purchases or local profiles into sessions. Do not silently wipe unrelated preferences or change the HOLO visual identity. Resolve template/plugin dependencies with tests before removal. Human approval requested first for containment, diagnostics/RLS changes and the test/toolchain scope above.
