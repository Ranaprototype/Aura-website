# Architecture decision records · Phase 1

Status of all entries: **recommended for review**, not deployed or provider commitments. Baseline facts are in the [Phase 1 report](AURA-PHASE-1-REPORT.md). Revisit a choice when its stated assumption no longer holds.

| ADR | Choice and why | Alternative considered / cost and downside | Dependency or revisit trigger |
|---|---|---|---|
| 01 · Deployment unit | Extend existing Express app as a modular monolith. Domain-owned command/query interfaces and explicit transaction scope fit stock, order and campaign invariants. | Per-domain services introduce network failures, distributed reconciliation and more deploy/on-call units. One release instead couples deployments and can concentrate load. | Enforce imports and ownership in review/tests. Extract only for measured isolation/scale requirements and a durable interface, not the number of domains. |
| 02 · Record and transaction authority | PostgreSQL for canonical state, including spec revisions, binding consent and money. Keep current Supabase diagnostic adapter; propose backend-only pooled SQL for multi-module transactions with narrow grants/RLS. | Browser PostgREST CRUD or multiple HTTP writes cannot by themselves atomically reserve stock and create an order. A narrowly scoped versioned DB function is a viable alternative; concentrates domain code and review in SQL. | Verify host supports pool mode, transaction-local role context, backup/restore and non-owner access. Driver/host/region not selected. Connection limits and schema migration overhead are real costs. |
| 03 · Identity and tenancy | Favor managed OIDC identity plus backend session; model org membership and resource-specific grants in PG. Multi-vendor order projections restrict exposure. | Custom passwords increase security/recovery burden; long-lived browser JWTs complicate revocation. DB-per-tenant improves hard isolation but complicates cross-vendor checkout, migrations and support. | Validate IdP cost, MFA, data region, recovery and SLA. Test pooled context and suspension. Dedicated DB isolation may be justified for contractual tenants later. |
| 04 · Frontend and API | Preserve React/HOLO routes and style system. Same-origin API with explicit versioned DTOs; anonymous local selections are untrusted input only. | Rewrite or client-direct domain CRUD speeds prototypes but risks losing the UI, duplicating pricing and widening permissions. API adds an extra hop and contract tests. | Agree compatibility/deprecation policy; preserve direct-link and browser tests. No unsafe fallback to local payment/account success. |
| 05 · Jobs and delivery | PG outbox + transactional inbox, leased workers from same codebase, bounded retries/reconciliation. Redis optional for disposable coordination only. | Inline remote calls hold locks and can double-charge on retries. Separate broker now adds hosting, consistency gaps and monitoring. Outbox polling costs DB capacity and needs pruning. | Measure backlog, lease expiry, DB I/O and job age; add queue transport if warranted while retaining PG as authoritative record. |
| 06 · Media and revisions | Store large bytes in private versioned object storage; PG records hash, ownership, checks and durable links. Share reviewed snapshots not mutable private originals. | Database blobs simplify one backup but inflate WAL/restore time. Public-by-default buckets ease delivery but cannot reliably protect private designs. | Budget egress, transforms, quarantine and retention. Reconcile orphan objects and verify cross-store recovery before promotion. |
| 07 · Financial boundary | Hosted checkout, immutable quote/order allocations, provider-verified settlement and human-authorized refunds. Treat provider uncertainty as pending reconciliation. | Collecting card details is prohibited. Redirect-based confirmation is cheap but unauthenticated. Provider-specific hosted flow costs fees and constrains UX but minimizes card-data scope. | Finance/legal must select merchant of record, marketplace settlement, supported currencies, tax, refunds, authorization expiry and dispute handling. No live credentials. |
| 08 · Campaign contracts | Separate interest, assent, funding and production. Immutable terms and quote versions, serialized cancellation/close and explicit release. | Converting votes to orders or updating live terms is simpler but has no informed assent. Per-commitment versioning and reconciliation add review, dispute and storage costs. | Decide jurisdictions, legal consent evidence, eligibility, partial funding, cancellation, expiry and refunds. Do not enable a campaign until enforceable terms and funding workflow are approved. |
| 09 · AI and discovery | Capability-bound adapters, versioned prompts/jobs, owner-scoped retrieval, explicit cost ceiling. Relational filters/approved catalog first; evaluate PG vector search only if justified. Outputs draft or advise, never authorize. | One general autonomous agent or external vector DB at launch expands leakage, vendor lock-in, operational and inference costs. Abstraction requires test corpora and model evaluation; embeddings require refresh/deletion. | Product/privacy owners approve provider terms, unit economics, relevance benchmarks and human approval policy. No provider is authoritative for price, stock or feasibility. |
| 10 · Environment and operations | Prefer static frontend + same-origin API ingress, isolated environments, managed PG where controls permit, private worker/storage when necessary. CI verifies; release promotion separate and human-approved. | Public dev server, shared DB/keys or automatic production promotion reduce setup effort but expand incident scope. Managed hosting reduces operations at cost of fees and dependency on regional recovery capabilities. | Infrastructure owner must approve hosting, workload budgets, alerts, retention, restore drill and RPO/RTO. No infrastructure ordered or deployed. |

## Decision gates, not implementation tasks for this phase

1. Product + legal + finance: select seller/merchant model, quote/commitment/cancellation terms, fulfillment liability and approval thresholds.
2. Security + DB owners: establish target-side migration/grant metadata, decide identity/session integration, membership model, trusted connection path and RLS test matrix. Authorize any external inspection separately.
3. Data + privacy + operations: approve classification, regions, deletion/legal holds, model consent, spend limits and recovery objectives. Keep historical checkout/credential incident on a separate response track.
4. Engineering: prototype only after scope approval, using isolated fixtures. Verify contention, duplicate callbacks, outbox retry, revocation and tenant-safe reads before opening any protected operation. Record accepted/rejected ADRs and accountable owners in the subsequent review.
