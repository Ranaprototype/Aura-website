Do not use this table for customer or sensitive data.

Readiness selects only `id` with GET and a one-row limit. An actual upstream 200/206 JSON response containing zero or one UUID row is required; an empty HTTP body is not an empty relation. The adapter rejects non-success wire statuses before SDK normalization and checks row shapes after parsing. Operator reads are capped at 50; writes are trimmed and bounded at the API, not by a database check constraint. An anon/publishable key is not an administrative credential and its effective privileges still depend on the target. It does not certify Supabase default grants or target-side security.

## Later data ownership (no speculative tables)

Identity owns principals/memberships; customer, seller and manufacturer domains own scoped profiles. Catalog owns categories/variants; inventory owns reservations; orders own quote snapshots and commitments; payments/refunds own provider identifiers and idempotent state; shipping owns fulfillment. Design/3D own revisions and object references, community owns visibility/consent, Product Lab owns demand signals, manufacturing owns quotes and production commitments. Operations owns approval records, notifications and sanitized security events. Use foreign keys, tenant-scoped uniqueness, query-backed indexes, UTC-aware timestamps, currency plus integer minor units or explicit decimal scale. Commit stock/commitment changes transactionally; test contention before accepting orders. Redis or browser state must never be the source of record.

### Keys, principals and isolation

Prefer opaque UUID PKs (not authorization), `timestamptz` for instants, explicit effective/expiry times and integer minor units **with currency** and currency-specific scale. Avoid floats in authoritative pricing; separate currency totals rather than silently converting. Use positive-quantity/nonnegative-balance checks, uniqueness for external IDs in their provider/account scope and monotonic version fields for optimistic writes. Use foreign keys for real relationships; for org-owned children include `(org_id, parent_id)` referencing a parent unique on that pair. Do not force customer-owned private designs into a seller tenant. Multi-vendor customer orders are deliberately split; manufacturers get a separate project-specific grant, not all customer records. Explicit public projections are narrower than private records.

For future authenticated business data, propose backend-only transactional SQL with a scoped non-owner login (see ADR-02). Set verified principal/org **transaction-locally**, never trusting browser-supplied roles or leaking session state on pooled connections. Isolation rules combine capability, active membership, owner and explicit sharing grants. Default deny, apply both row visibility and write checks; consider FORCE RLS for owner-path hazards, but never use superuser/BYPASSRLS for request processing. Minimize grants on base tables, views, sequences and callable functions; review view execution privileges, default privileges and function search paths. Worker privileges limited to job/domain tasks. Test independent DB sessions for same-tenant allow, cross-tenant deny, revoked membership, private-to-public projection and pool reuse; test via direct DB/API exposure as well as Express. Approval required for identity propagation and privileged operations design.

### Identity on a pooled SQL connection (target contract)

For a user request, the trusted assertion flows **verified server-side session → backend transaction → RLS**. PostgreSQL authenticates the backend login, not the human behind it. RLS evaluates row policies; it does **not** authenticate arbitrary custom variables. A principal or organization stored in a setting is trustworthy only because untrusted callers have no access to the SQL connection or to any interface that can set that context.

1. Verify the server-side session is active; derive the principal from its subject mapping. Never take the actor or role from browser headers, body fields, URL parameters or local storage. An organization ID may select a requested organization; it proves no membership.
2. Check out a connection using the restricted application login and begin an explicit transaction. Bind the verified principal transaction-locally. Resolve the active organization membership, current permissions and applicable resource grants from authoritative records within that transaction; only then bind the authorized organization transaction-locally. Keep the membership lookup narrowly scoped to the verified principal. Deny missing, malformed or inconsistent context; never fall back to a default tenant.
3. Execute every protected query through the same transaction handle. Use parameterized transaction-local settings (`set_config` with its local flag set to true), **never** persistent session-level settings. The pooler must keep the transaction on one physical backend until commit or rollback; statement pooling and separate autocommit calls are unsuitable. Do not hold that connection across provider calls.
4. Commit on success; roll back on denial, exception, timeout or cancellation. Release only after the transaction is known to have ended; discard a connection of uncertain state. Start each checkout without usable identity and bind anew. Commit and rollback must both remove the transaction's identity; this design must not depend on overwriting a previous borrower's session-level settings.

**Revocation:** once revocation commits, the next protected authorization decision must deny access, even with the same still-valid login session. Do not grant access from cached membership or stale token roles. Serialize sensitive writes with revocation (for example, lock and recheck the membership row before mutation); whichever commits first determines the ordering. A transaction-local setting is not a durable delegation, and revocation cannot recall data already returned.

**Separate access paths:** authenticated business data uses backend-only SQL over restricted network paths with server-held credentials. No client SQL console, generic SQL RPC, context-setting RPC or client-selectable database role. Restrict direct connections to approved workloads and separately controlled operator access. Browser-facing PostgREST is not an alternative login to that backend role. By default neither `anon` nor `authenticated` needs any private schema/table/sequence or function access. If explicitly approved for public catalog reads, allow only schema usage and SELECT on named, published-field projections: no base-table access, writes, privileged functions, role assumption or context manipulation. Check inherited, `PUBLIC` and default privileges and view execution rights, not just direct grants. A publishable key is public, not an authorization decision. These are required permissions, **not verified deployed grants**.

### Atomic transitions and queries

- Reserve stock with a guarded conditional update or locked balance rows in stable order; create hold and its expiry atomically. Fail the whole checkout transaction if any line is unavailable. Reprice on server, reject changed terms pending customer consent. Order snapshot, reservation and outbox commit together. Release/consume holds idempotently on expiry or verified payment; late capture after expiry goes to reconciliation, not automatic overselling.
- Lock campaign state for accepting/cancelling commitments and for closing at the deadline. Evaluate only eligible, non-cancelled commitments under the pinned terms and funding rule. Persist a single close result and outbox atomically; materialize orders in bounded, deduplicated batches if necessary. Below threshold: lapse/release holds, reconcile provider void/refund; no production. Above: await funding/authorized production release. Locking/retry tests must cover last-unit and cancel-versus-close races.
- Insert verified webhook receipt, apply allowed state change and emit outbox in one transaction; serialize refunds against captured and already reserved/refunded amounts. Rejected/out-of-order transitions cannot regress a settled state. No provider call or image processing inside a DB transaction. Audit high-risk mutation and approval consumption with the state change.
- Index FK joins and scoped access paths based on measured plans: e.g. `(seller_id, status, created_at, id)` for vendor queues, `(campaign_id, status)` for close, partial indexes for active holds by expiry and unprocessed outbox by next-attempt. Cursor queries have a unique tie-breaker. Filter tenant and visibility before ranking/search; embeddings and cached counters are rebuildable, never commitments. Observe write amplification before adding text/vector indexes.

### Lifecycle and change safety

Separate reversible private profile data from immutable commercial snapshots and approval receipts. Define retention by record class: short-lived sessions/jobs and quarantined uploads expire; withdrawal removes publication/search/CDN access and stops further processing; financial obligations, disputes, moderation evidence and legal holds may require restricted retention. Pseudonymize where lawful; do not cascade profile deletion into order/payment ledgers. Track deletion through object versions, providers, search, caches and backup expiry; reapply deletions after restore. Jurisdiction, retention periods, RPO/RTO and evidence ownership are **pending decisions**, not promises of immediate erasure.

Future migrations: version-controlled additive change → dual-compatible readers/writers → bounded resumable backfill → validate constraints/permissions → later contract after old binaries retire. Verify applied ledger and drift first; test clean install, upgrade with fixtures, application rollback against expanded schema, concurrent readers and restore. Use transaction-safe DDL where supported; schedule non-transactional index builds separately. On failure stop rollout, roll application back if compatible or use a reviewed forward fix; destructive restore requires owner-approved recovery and reconciliation of provider events. Do not invent down migrations that discard data.
