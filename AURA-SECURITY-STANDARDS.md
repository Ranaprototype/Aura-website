# Security standards and current limits

**Current disposition: local development only.** No real sign-in, memberships, checkout, order API or live provider. Keep protected actions unavailable until there is a verified principal, server-side ownership checks, session lifecycle and negative tests. A diagnostic bearer credential is not a user role. Local wishlist and cart may be edited by the device user; never promote them into trusted prices, identities or orders.

- No PAN, expiry or CVC in app input, state, persistence, tests, logs or API contracts. Future hosted checkout requires separate approval; redirect/UI success is never a settlement signal. Historical checkout, profile, address and order keys are neither hydrated nor migrated by the replacement flows. No deletion or remediation script ships.
- **Separate incident track — OPEN / exposure unverified.** The baseline had unsafe browser persistence. Owners must identify affected builds/origins, distribution dates, telemetry recipients, backups, relevant duties and approved response procedures. Do not inspect, export or erase browser records as part of development. Do not roll back to a collecting checkout. Credential exposure reported in historical `SECURITY.md` requires owner rotation evidence. Neither incident is closed by a local code change.
- Runtime accepts only a configured publishable key or a legacy key with an anon role claim (format guard, not identity verification). No service-role key is needed. Never place a secret under `VITE_*`. `.env.example` is inert; keep credentials outside Git/build artifacts. Never provision shared targets from tests.
- The application and dev proxy bind loopback. Only an explicitly enabled local operator can use message diagnostics. Origin-bearing requests cannot use the operator path. No account cookies are issued. Future cookie auth requires Secure/HttpOnly/SameSite settings, expiry/revocation, request-origin and CSRF defenses, rate limits and cross-tenant tests. Denying an unsupported route today is not a working auth system.
- No replay/console collector, credentialed storage proxy or Manus runtime injection in the active Vite config. Do not log request bodies, credentials, database error details or client stacks. Use generic API errors and allowlisted event fields. Non-sensitive correlation IDs, authorization audit records, trusted proxy policy, rate limiting and reviewed CSP/TLS remain requirements before shared exposure.
- There is no upload service. Require object-level authorization before any signed URL, private buckets, size/type validation, retention and deletion policy when one is approved. No dependency audit proves application safety; recheck lockfile, tooling and runtime at each change.
