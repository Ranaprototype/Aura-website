# Security architecture · proposed controls and release gates

## Current posture and non-negotiable boundary

The merged preview has no user-session or commerce API. Checkout cannot accept payment details; confirmation cannot establish a purchase. Diagnostic bearer access is not a customer/seller session. Preserve these denials until the corresponding controls are implemented and independently verified. Prior unsafe checkout persistence and possible historical credential exposure are **separate, open owner-led incidents** (see [current standards](AURA-SECURITY-STANDARDS.md) and [historical record](SECURITY.md)). Do not inspect, migrate or delete historical browser records, infer exposure or claim remediation beyond the current source.

## Threats and target controls

| Trust boundary / failure | Required control | Acceptance evidence before enabling |
|---|---|---|
| Browser → Express: forged identity, CSRF, stolen session | Proposed managed identity provider + server-managed opaque session. Verify issuer/audience/signature/expiry, OAuth state, nonce and PKCE; link by provider subject, not email alone. Rotate session on login/elevation, revoke on logout/password change/role loss; idle and absolute expiry. Host-only Secure/HttpOnly/SameSite cookie over TLS; explicit origin/CSRF checks for unsafe methods. No tokens in web storage, URLs or telemetry. IdP owns password hashing/recovery; MFA and step-up for sensitive roles. | Negative callback/session fixation/replay/CSRF tests; revoke existing sessions and confirm denial. No local marker promoted to identity. |
| API → DB: cross-seller/customer disclosure, privilege escalation | Default-deny object policy plus scoped SQL/RLS, verified membership at use, parameterized queries, restricted views and non-owner role. Cross-org access requires resource-specific grant. Reject actor/price/role fields in client data. | Two-tenant tests for detail, list, export, counts, search, worker and direct DB; negative grants reviewed under actual runtime role. |
| Buyer → provider → AURA: forgery, replay or duplicate capture/refund | AURA never collects PAN, expiry or CVV, including UI state, support tools, logs and tests. Use provider-hosted checkout; only opaque references server-side. Customer confirms server-calculated amount/currency. No payment credentials in browser storage, logs or analytics. Verify signed raw webhook, freshness, provider account, amount/currency/order; unique inbox event and constrained transitions. Reconcile missing/out-of-order events with authenticated provider reads. | Forged, stale, duplicate, mismatched and delayed events cannot mark paid; redirect cannot confirm; concurrent partial refunds cannot exceed captured balance. No real provider calls without approval. |
| User media → storage/CDN → processor/AI: disclosure or hostile files | Server-chosen per-owner key, private-by-default, least-privilege signed upload/read, quarantine, allowlisted formats, byte/pixel/mesh/batch limits, safe decoding, malware scan, remove metadata; isolate processing without arbitrary network/filesystem access. Publish only cleared derivative with consent. | Unauthorized reads and stale grants denied; oversized/mislabeled assets rejected; unpublish invalidates delivery/index paths. Signed URLs are bearer grants: short TTL, never logged. |
| Community/search/model → other users: XSS, prompt injection, confidential retrieval | Escape rendered text; sanitize any supported rich media. Scope search **before** retrieval and again at delivery; no mixing private tenant indexes/caches. Treat prompts, comments, images and tool output as untrusted content, never instructions to grant access. Rate-limit social abuse, moderation reports and upload/AI budgets. | Private draft cannot surface in another tenant's retrieval, recommendation, public CDN or logs. Takedown revokes access to derived content where required. |
| Operator/agent → domain services: unauthorized change | Scoped command allowlist, short-lived delegated context, no SQL/admin tokens or financial tools for autonomous execution. Admin use requires MFA, purpose, case, approval where required, bounded time and independent review. | Denied cross-role commands, expired approvals, changed proposal contents and replay attempts leave state unchanged; break-glass review tested. |

## Permission and approval model

Anonymous users read **published** projections only. Customers own their private drafts, profile, commitments and order history. Seller staff manage their organization's listings/stock and allocated order lines; no other vendors' lines, payment credentials or full customer profiles. Manufacturer staff see only invited spec revisions and their own feasibility, quote and batch records. Independent reviewers release quality gates; moderators manage visibility, not financial records. Administrators perform scoped commands, not unrestricted database edits. Memberships may overlap; acting organization and purpose must be explicit. Suspension and grant revocation apply to queued work as well as interactive access.

For spend, commitment, refund, production release, capability verification or privilege escalation, bind a human authorization to **who, acting role/org, action, target/version, amount/currency or terms hash, expiry and purpose**. Customer authorizes own purchase/commitment and can cancel only under pinned terms and applicable rights. An authorized operator other than the requester approves privileged refunds/adjustments. Manufacturer reviewer signs feasibility/quote; campaign owner authorizes close/release subject to recorded conditions. Agents may propose or summarize, not authorize payments/refunds/commitments; workers can execute an already-approved command once, within scope, after rechecking membership, version, limits and approval validity. Invalidate and request fresh approval when terms change. Record denial and approval consumption, prevent replay. Final legal/payment/refund and separation-of-duties rules require owner sign-off.

## Identity boundary: verification gate before protected data access

The browser presents a session credential, not an authoritative user ID, tenant or role. Only the backend verifies the server-side session, resolves current authorization and supplies transaction-local SQL context. Neither a custom database setting nor an RLS policy verifies the caller's identity. Follow the [pooled SQL transaction contract](AURA-DATABASE-ARCHITECTURE.md#identity-on-a-pooled-sql-connection-target-contract). Keep application SQL credentials, service-role keys and migration/admin secrets entirely outside the browser. The existing local diagnostics flow is not this identity mechanism.

Required future acceptance evidence, using synthetic tenants, the actual planned pool mode and effective non-owner roles in an isolated environment (**not executed in Phase 1**):

| Check | Required result |
|---|---|
| Authorized member of A | May read and perform a permitted write on A's fixture; a read-only member cannot write. |
| Cross-tenant access | The same caller cannot read B's row, list it, mutate it or create a child under B's parent. Verify no data change, not just a response code. |
| Immediate revocation | Revoke and commit membership while retaining the session; the very next read and write are denied without waiting for token expiry. Test concurrent revocation against a sensitive write under the documented ordering. |
| Caller cannot change identity | Submit conflicting user/org/role hints via headers, URL and JSON. No hint changes the verified principal, grants membership or elevates the SQL role. Unauthorized org selection fails before protected work. |
| Pool reuse | Force A, B and an unbound request onto the same physical backend in sequence. Repeat after A commits and after A rolls back/errors. B sees only B; the unbound request has no usable context and cannot read or write protected rows. |
| Paths outside Express | With public/ordinary authenticated PostgREST credentials, private tables and mutating or context-setting RPCs remain inaccessible; only expressly approved public projections are readable. From a client network, direct SQL access to the application role is denied. |
| No privileged credentials in the browser | Build with synthetic server-only secret canaries; verify absence from shipped bundles/source maps, HTML, network responses and browser storage. Check deployment config does not export private keys via public build variables. Never use production secrets as fixtures. |

## Secrets, privacy and audit

Separate environment-specific issuer keys, webhook secrets, model budgets, storage grants, runtime and migration credentials; rotate with overlap and revocation tests. Secrets stay in an approved server-side secret store, never in Git, Vite public variables, images, browser storage or error strings. Restrict egress to configured providers; no arbitrary user/agent URLs. Limit payload depth, rate, concurrency and CPU; protect ingress and deliver CSP/TLS after compatibility tests. Log sanitized actor/role/org, resource ID/version, operation, request ID, purpose, authorization decision, approval ID and transition; no raw bodies, prompts, addresses, tokens or cards. Restrict append-only audit access, monitor privilege changes, separate retention/legal holds from product deletion. Encrypt at rest and in transit; classify private designs/IP, addresses, contacts, manufacturer quotes and model inputs before transfer. Require consent, region and no-training/retention terms; no private content in shared model evaluation without permission.

**Unverified:** target Supabase grants, IdP/provider selection, direct network paths, secrets rotation, residency, real rate limits, incident scope, supplier contracts, backup restore and operator staffing. This design is not a security certification and does not authorize connecting or deploying anything.
